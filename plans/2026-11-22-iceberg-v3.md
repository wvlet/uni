# Iceberg format version 3: read and write

## Goals

- Read Iceberg v3 tables that other engines write. DuckDB, Spark, Trino, and Snowflake can now create v3 tables, and today `Parquet.dataset` refuses them when it opens them.
- Write v3 tables: create them, and append and overwrite on tables that are already v3, so Uni can work with them as well as read them.
- Keep v2 as the default for new tables. Most engines still create v2 by default, and v2 reads everywhere.

## Background

- The reader accepts versions 1 and 2 (`IcebergTable.MaxFormatVersion`). The writer commits only to version 2 tables, and fails on types v2 can't hold (nanosecond timestamps among them).
- The changes in v3 that affect Uni:
  - **New types.** `timestamp_ns` and `timestamptz_ns` (INT64 NANOS in Parquet), `unknown` (always null, never stored in files), and `variant`, `geometry`, and `geography`.
  - **Default values.** A field's `initial-default` fills it in data files written before the field was added. `write-default` matters only to writers.
  - **Deletion vectors.** Row deletes are a roaring bitmap stored in a Puffin file. The manifest entry names the data file it applies to (`referenced_data_file`) and gives its byte range (`content_offset`, `content_size_in_bytes`). v3 writers no longer write v2 position-delete files.
  - **Row lineage.** Metadata gets `next-row-id`. A snapshot gets `first-row-id` and `added-rows`. A data manifest in the manifest list gets `first_row_id`. Writers must keep these; readers may expose `_row_id`, but don't have to.
- DuckDB 2.0's iceberg extension writes v3 tables (through a REST catalog), including deletion vectors. With the Iceberg Java REST fixture, it can make realistic test tables locally. pyiceberg 0.12 can't write v3 yet.

## Design

Lane: Standard. This is new user-facing behavior. The user set the direction ("support Iceberg v3 both for read/write") and authorized auto-merge, so the series goes ahead without a design card.

The work ships as three PRs. Each one is useful on its own.

- **PR 1: read v3 tables without deletes.**
  - Accept `format-version` 3.
  - Read `timestamp_ns` and `timestamptz_ns` as INT64 NANOS timestamps, with manifest bounds so filters can skip files.
  - Read an `unknown` column as all nulls.
  - A top-level primitive column that a data file lacks reads as its `initial-default` instead of null. Filters see the filled value.
  - Still fail, naming the reason: delete files and deletion vectors (until PR 2), `variant`, `geometry`, `geography`, a non-null `initial-default` on a nested field, and encrypted tables.
  - Row lineage is ignored on read. Uni doesn't expose metadata columns.
- **PR 2: apply row deletes.**
  - Apply deletion vectors (Puffin blob `deletion-vector-v1`, portable 64-bit roaring bitmap) and v2 position-delete files, both matched to data files by path and sequence number.
  - Equality deletes keep failing by name. DuckDB never writes them, and they need per-row value matching.
- **PR 3: write v3 tables.**
  - A table property on create (`format-version` = 3) makes a v3 table. Appends and overwrites keep the table's version.
  - On v3 tables, commits keep row lineage: snapshot `first-row-id` and `added-rows`, metadata `next-row-id`, and manifest-list `first_row_id`.
  - v3 tables accept nanosecond timestamps.
  - Every other table operation (alter, expire, rename) works on v3 tables, and each commit preserves the v3 fields.
- **PR 4: read `variant`, `geometry`, and `geography`.** Variants (shredded or not) decode to Scala values, in plain Parquet files too; geospatial columns read as WKB bytes. Writing them stays out of scope.
- Tests cover v3 fixtures made by DuckDB, checked into the test resources next to the pyiceberg ones, and Uni-written v3 tables read back by DuckDB.

## Alternatives and Why Not?

- **One large PR.** Deletes and row lineage are independent pieces. Splitting them keeps each review small, and v3 reads land first.
- **Treat v3 as v2 and ignore new fields.** That would silently return deleted rows and wrong nulls for defaulted columns.
- **Hand-edit v2 fixtures into v3.** Real DuckDB output catches layout details (Puffin offsets, manifest fields) that a hand edit would guess.
