# Upgrade uni to Scala 3.9 (LTS)

Date: 2026-09-03

## Context

Scala 3.9.0 is the new LTS. Scala Steward already bumped the main build
(`build.sbt` `SCALA_3 = "3.9.0"`) and `examples/electron-app` in #688, and that
PR auto-merged. But it left main **red**: the "sbt plugin scripted test" job
(not a required check) fails with

```
Forward incompatible TASTy file has version 28.9, produced by Scala 3.9.0
expected stable TASTy from 28.0 to 28.8.
```

Root cause: `sbt-uni` runs uni **in-process** inside sbt's metabuild
(`sbt-uni/build.sbt` → `"org.wvlet.uni" %% "uni" % UNI_VERSION`). sbt 2.0.8's
metabuild compiles with Scala 3.8.4 (verified with `./sbt "eval
scala.util.Properties.versionNumberString"` → `3.8.4`; `sbt/sbt` tag v2.0.8 has
`scala3 = "3.8.4"`). A 3.8 compiler cannot read 3.9 TASTy, so the plugin can no
longer compile against a 3.9-built uni. sbt's `develop` branch already has
`scala3 = "3.9.0"`, but no released sbt ships it yet.

Everything else about 3.9.0 is in place: `nscplugin_3.9.0/0.5.12` exists on
Maven Central, Scala.js 1.22.0 is already pinned, and the JVM/JS/Native/
crossproject/playwright CI jobs passed on #688.

Goal of this PR: finish the 3.9 upgrade properly — fix the sbt-uni breakage,
move every remaining 3.8.x / 3.3.x pin and doc reference to 3.9, and record the
decision.

## Design

### 1. Decouple sbt-uni's in-process uni from the main build (the fix)

`sbt-uni/build.sbt`: replace the `UNI_VERSION`-driven library dependency with a
pinned release that was built with Scala 3.8:

```scala
// uni runs in-process inside sbt's metabuild, so it must be readable by the metabuild's Scala
// compiler. sbt 2.0.x compiles the metabuild with Scala 3.8, which cannot read TASTy produced by
// Scala 3.9 (uni's current SCALA_3). Pin the plugin's in-process uni to the last release built
// with Scala 3.8 until an sbt release moves the metabuild to Scala 3.9 (sbt's develop branch
// already has scala3 = "3.9.0"); then this can go back to UNI_VERSION.
val UNI_IN_PROCESS_VERSION = "2026.1.21"
...
libraryDependencies ++= Seq("org.wvlet.uni" %% "uni" % UNI_IN_PROCESS_VERSION),
```

Keep `UNI_VERSION` (env) for `scriptedLaunchOpts` `-Duni.version=` — the
scripted test *apps* are compiled with Scala 3.9 and must use the locally
published, 3.9-built uni.

Why this is safe:
- The plugin only uses `wvlet.uni.http.codegen.{HttpCodeGenerator, ServiceScanner}`
  (`sbt-uni/src/main/scala/wvlet/uni/sbt/UniPlugin.scala:20`). `ServiceScanner`
  uses plain Java reflection over compiled `.class` files
  (`uni/.jvm/src/main/scala/wvlet/uni/http/codegen/ServiceScanner.scala`), so it
  can scan classes compiled by Scala 3.9 while the plugin itself runs on 3.8.4.
- Codegen has not changed since v2026.1.21 (`git log v2026.1.21..HEAD -- <codegen> sbt-uni`
  shows only sbt/scalafmt bumps), so nothing is lost by pinning.
- `uni_3` 2026.1.21 POM depends on `scala3-library_3` 3.8.4 (verified).

Alternatives rejected:
- Compile sbt-uni with Scala 3.9: consumers' sbt 2.0.8 metabuild (3.8.4) could
  not read the plugin's TASTy → plugin unusable for everyone.
- Revert uni to 3.8.4 and wait for sbt: not what was asked; sbt 2.0.9 timing unknown.
- Vendor codegen sources into the plugin: drags in `wvlet.uni.log` etc.; more
  machinery than a one-line pin that is meant to be temporary.

### 2. Scripted tests for sbt-uni

- `sbt-uni/src/sbt-test/{codegen/rpc-client,codegen/rpc-client-with-provider,restart/basic,restart/workdir}/build.sbt`:
  `scalaVersion := "3.8.3"` → `"3.9.0"` (the app must be ≥ 3.9 to consume the
  3.9-built uni snapshot).
- `sbt-uni/src/sbt-test/codegen/{rpc-client,rpc-client-with-provider}/project/plugins.sbt`:
  drop the `libraryDependencies += "org.wvlet.uni" %% "uni" % uniVersion` line.
  It adds the *3.9-built* uni to the scripted app's **metabuild** classpath, which
  is exactly the TASTy clash again. It is not needed: the plugin brings its own
  uni transitively, and the generated client code is compiled in the `app`
  project, which already declares the uni dependency in `build.sbt`.

### 3. Sub-builds that stay on Scala 3.8 (deliberately)

`sbt-uni-playwright/build.sbt` `SCALA_3 = "3.8.2"` and its scripted test stay
as they are: those artifacts are loaded by consumers' metabuild and must match
sbt 2.0.x's Scala 3.8. `sbt-uni-crossproject` and `sbt-uni` use the metabuild
default already. No change.

### 4. Docs: uni now requires Scala 3.9+

Because a 3.9-built library needs a ≥ 3.9 compiler (TASTy forward-compat rule),
update the stated minimum and every sample `scalaVersion`:

- `docs/guide/installation.md`: `Scala 3.3+` → `Scala 3.9 (LTS) or later`.
- `docs/book/ch01-01-installation.md`: prerequisites row `3.3 or newer` →
  `3.9 or newer` (mention it is the current LTS and that uni's artifacts are
  compiled with it); `scala3Version = "3.3.4"` and `scalaVersion := "3.3.4"` →
  `"3.9.0"`.
- `docs/mcp/index.md` and `docs/http/electron-tutorial.md`: `"3.8.4"` → `"3.9.0"`.
- `docs/build/sbt-uni.md`: add a short note in the "sbt 2.x" tip that the plugin
  bundles a uni build matching sbt's metabuild Scala (3.8), independent of the
  uni version the project itself depends on.

### 5. ADR + plan file

- New `adr/2026-09-03-sbt-uni-in-process-uni-pin.md` + index entry in
  `adr/README.md`: why sbt-uni pins its in-process uni to a 3.8-built release,
  how to lift the pin (when a released sbt's metabuild is on 3.9), and the
  "no uni dep in scripted metabuild" rule.
- Copy this plan to `plans/2026-09-03-scala-3.9-upgrade.md` (per CLAUDE.md).

### CI

`test.yml`'s "sbt plugin scripted test" job still does `publishLocal` of uni and
passes `UNI_VERSION` → used only by the scripted apps now. In
`release-sbt-plugin.yml` the "Publish uni locally for plugin dependency" step and
the `UNI_VERSION` env line are removed: the plugin resolves its pinned uni from
Maven Central and that job never runs scripted, so the step was dead work.

## Verification

1. `./sbt compile` and `./sbt coreJVM/test uniJVM/test` (sanity on 3.9.0, already green in CI).
2. Reproduce the CI flow locally:
   ```
   ./sbt "coreJVM/publishLocal; uniJVM/publishLocal"
   UNI_VERSION=$(./sbt "print uniJVM/version" ... )   # as in test.yml
   cd sbt-uni && UNI_VERSION=... ../sbt "scalafmtCheckAll; publishLocal; scripted"
   ```
   All four scripted tests must pass; before the fix, `publishLocal` fails with the
   TASTy 28.9 error.
3. `./sbt scalafmtAll`, plus `scalafmtCheckAll` in sub-builds touched (sbt-uni).
4. Push, open PR, watch CI: the "sbt plugin scripted test" job must go green.
