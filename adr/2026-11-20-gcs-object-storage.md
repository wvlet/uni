# Native Google Cloud Storage in uni

## Context

`S3Config.gcs` reached Google Cloud Storage through its S3 interoperability API, which needs HMAC keys. Most Google Cloud projects never create them, and organization policies often forbid them. Users want GCS with the credentials a project already has (service-account keys, `gcloud auth application-default login`, the metadata server), through the same `ObjectStore` API and on the same three platforms as S3, with no Google SDK. The S3 ADR (`2026-11-20-s3-object-storage.md`) expected this as a second `ObjectStore`.

## Decision

- **`GcsObjectStore` on the JSON API**, next to `S3ObjectStore` in `wvlet.uni.storage`. Listings, metadata, and errors are JSON, which Uni already parses; the XML API would have grown the private `S3Xml` reader. Media downloads (`alt=media`) honour `Range`. Object names are one path segment (`/storage/v1/b/{bucket}/o/{name}`, `/` sent as `%2F`), unlike S3's per-segment key encoding.
- **Resumable uploads for streams.** `newOutputStream` buffers 8 MiB chunks (a multiple of 256 KiB, as Google requires); a stream that never fills one sends a single media upload. Each chunk is sent with `X-GUploader-No-308: yes`, so Google answers 200 with `X-Http-Status-Code-Override: 308` instead of a 308 that browser `fetch` with manual redirects can't read. The `Range` header says how much Google committed, which can be less than was sent; the rest stays in the buffer and goes with the next chunk. Three answers in a row that commit nothing fail the upload instead of looping. `abort()` (and any failure) DELETEs the session without retries, since the HTTP client retries Google's 499 answer by default.
- **Session URIs are credentials.** Google treats a resumable session URI as an auth token, so it never appears in logs or exception messages, no bearer token is sent to it, and a `Location` on another host than the endpoint is refused.
- **Pure-Scala RSA on every platform.** Service-account JWTs (RS256) and V4 signed URLs (`GOOG4-RSA-SHA256`) need RSASSA-PKCS1-v1_5 with SHA-256. Scala Native has no `java.security`, but `java.math.BigInteger` and `java.util.Base64` exist on all three platforms, so `Rsa` reads PKCS#8 (and PKCS#1) PEM keys with a small DER reader and signs with the CRT parameters. One code path means the signer the JVM tests check against `java.security.Signature` is the one Native and JS run. Limiting signing to the JVM and Node would have left Native without service accounts and signed URLs, and needed a Node `crypto` binding for the same result.
- **RSA blinding.** `BigInteger.modPow` is not constant time, so the private operation is blinded. The blinding factor comes from HMAC-SHA256 keyed by the private exponent over the message, the time, and a counter, because Scala.js and Native don't have `SecureRandom` in every setup; it is unpredictable without the key, which is what blinding needs. Each signature is verified with the public exponent before it is released.
- **Credentials in Application Default Credentials order:** `GOOGLE_APPLICATION_CREDENTIALS`, the gcloud file (`$CLOUDSDK_CONFIG`, `%APPDATA%\gcloud`, or `~/.config/gcloud`), then the metadata server (`GCE_METADATA_HOST` or `169.254.169.254`, checked by the `Metadata-Flavor: Google` answer, 1–2 s timeouts, no retry). Unlike the AWS chain, which skips a failing provider, a source that exists but fails (a malformed file, an unsupported `type` such as `external_account`, a revoked refresh token) raises `NoCredentials` or `InvalidCredentials`, as Google's libraries do, instead of silently switching identity. Only "no source here" (no file, no metadata server) moves on.
- **Token caching.** Each provider caches its token until 5 minutes before it expires and fetches a new one under a lock, so a long resumable upload makes one token request. The chain remembers the provider that answered.
- **Token endpoints must use HTTPS** (plain HTTP only to loopback, for tests), since the request carries a signed assertion or a refresh token and client secret. Errors keep Google's OAuth `error` and `error_description`, never the request.
- **`presign` moved onto `ObjectStore`.** GCS signs V4 URLs for the XML API host with the service account's key, reusing SigV4's canonical request and query encoding. Metadata-server credentials sign through IAM Credentials `signBlob`, so GKE and GCE workloads can share URLs without a key file. User credentials can't sign and fail with `NoCredentials`. The signer is checked against Google's conformance vectors (`googleapis/conformance-tests`, `v4_signatures.json`), since fake-gcs-server doesn't verify signatures.
- **`STORAGE_EMULATOR_HOST`** points the store at an emulator and makes the default credentials anonymous, the convention Google's own libraries use.
- **Shared pieces moved to `StorageSupport`:** HTTP-error unwrapping, range chunking under Node's `maxResponseBytes`, range response handling, and the lazily created clients, used by both stores.
- **CI runs fake-gcs-server**, a pinned, checksum-verified release binary, in the JVM job (`-public-host` and `-external-url` so session URIs point back at it). The tests are skipped unless `UNI_GCS_TEST_ENDPOINT` is set. fake-gcs-server checks no credentials, so a JVM test runs a local fake of the token endpoint, metadata server, IAM `signBlob`, and an upload session that commits only part of each chunk.

## Consequences

- `Parquet.openGcs` / `openGcsAsync` and `ByteSource.ofGcs` read Parquet from GCS; `Parquet.newWriter[A](store.newOutputStream(uri))` writes, and a failed write cancels the upload.
- Browsers use an explicit access token or signed URLs; the providers fetch tokens with the sync HTTP client, which browsers don't have.
- Workload identity federation (`external_account`), impersonated service accounts, `signBlob` for user credentials, and parallel chunk uploads are left out.
