# PTYs on the JVM and Scala Native: `PosixPty` through `posix_spawn`

## Context

`wvlet.uni.cli.term.PtyProcess` (see `2026-11-04-terminal-emulator.md`) had only a Scala.js backend, `NodePty`. JVM and Native apps need to run a shell behind `TerminalEmulator` too. Uni has no dependencies beyond the Scala standard library, so pty4j or JNA are out. It already calls libc through FFM on Java 22+ (`PosixTerminal`) and through libc-only C shims on Native (`uni_term_shim.c`).

## Decision

- `PosixPty.spawn(file, args, options)` returns a `PtyProcess` on the JVM and Native, with the same arguments as `NodePty.spawn`. `PtyOptions` moved to the shared sources. `PosixPty` and its lifecycle code live in `uni/.jvm-native`, a source folder the JVM and Native builds share (`jvmNativeSharedSources` in `build.sbt`). It is not in the shared sources because Scala.js cannot link threads or `CountDownLatch`, and a JS stub would only mislead.
- Both platforms take the same steps: `posix_openpt`, `grantpt`, `unlockpt`, then the slave's name (`ptsname_r` on Linux, `TIOCPTYGNAME` on macOS, since `ptsname` is not thread-safe). Then `posix_spawnp` with `POSIX_SPAWN_SETSID`, an empty signal mask, default dispositions, and file actions that open the slave as fd 0 and dup it to fds 1 and 2. A session leader without a controlling terminal that opens a terminal acquires it, on Linux and on macOS (checked on macOS 26: `tty`, the foreground process group, and SIGWINCH). The JVM calls these through FFM, and Native through `uni_pty_shim.c`.
- No `forkpty`. On glibc before 2.34 it is in libutil, which would add a link flag to every downstream Native binary (the trap in `2026-07-06-curl-shim-weak-linking.md`). `fork()` is also unsafe in a multithreaded JVM or Scala Native process, because the child would run managed code in a copy of every thread's state.
- The size is set on the slave, held open in the parent until the child has started. macOS resets a size set on the master when the slave is first opened. The master gets `FD_CLOEXEC`, so programs started by other threads do not keep the PTY open.
- Lifecycle, shared by both platforms in `PosixPtyProcess` over a small `PosixPtyOps` interface:
  - A reader thread polls the master (100 ms) and decodes UTF-8 incrementally (`Utf8StreamDecoder`), so a character split across reads arrives whole.
  - Output that arrives before the first `onData` listener is buffered and goes to that listener.
  - A waiter thread reaps the child and lets the reader drain for up to 500 ms; a background job can keep the slave open forever. It then closes the master under the write lock, so a recycled fd number is never written, and fires `onExit`. A listener added later is called right away.
- Exit codes are the exit status, or 128 + the signal number, as shells report them. `kill()` sends SIGHUP, as node-pty and a closing terminal window do. After the exit, `kill`, `write`, and `resize` do nothing.
- Supported: Linux (glibc 2.29+ or musl 1.1.24+, for `posix_spawn_file_actions_addchdir_np`) and macOS 10.15+. On Windows and on JVMs older than 22, `spawn` throws `UnsupportedOperationException`, and `PosixPty.unsupportedReason` explains why. It never falls back to plain pipes, which would give the program no terminal. The PTY tests are reported as skipped there, not passed.

## Consequences

- JVM and Native apps can host a real shell in `TerminalEmulator`, and tests can drive TUIs through a real PTY.
- On Java 24+, the JVM prints the native-access warning on the first call unless it runs with `--enable-native-access=ALL-UNNAMED`, as `TerminalIO` already does.
- `write` is synchronous: it blocks while the PTY's input buffer is full (the program is not reading).
- Windows ConPTY could be added later behind the same `PosixPtyOps` split, under its own name.
