# Build NativeServer apps with the Boehm GC

- Status: Accepted
- Date: 2026-10-30
- Plan: [`plans/2026-10-30-native-server-keepalive.md`](../plans/2026-10-30-native-server-keepalive.md)

## Context

The RPC benchmark from #833 (`examples/rpc-native/bench`, `rpc-bench.yml`) failed on Linux under concurrent keep-alive load. On arm64 the server aborted within a second, and the kernel's slow core dump looked like a stall at ~1.6 req/s. On x86_64 it dropped kept-alive connections mid-request. The cause is not in uni. With several threads allocating at once, Scala Native 0.5.12's own collectors (Immix, the default, and Commix) free or overwrite objects that are still in use: [scala-native#5046](https://github.com/scala-native/scala-native/issues/5046), [#5160](https://github.com/scala-native/scala-native/issues/5160). In NativeServer this showed up as impossible `ArrayIndexOutOfBoundsException`s in the request parser and the ISO-8859-1 encoder, `ArrayStoreException: Invalid array copy`, and garbled responses. `NativeServer` runs every handler on a pool of worker threads, so any concurrent load can trigger it. uni's own Native tests link in debug mode and never hit it.

Measured with the benchmark build (release-full, full LTO), server on 2 cores, oha `-c 16` for 10 s:

- Immix with trap-based yieldpoints (the release default): arm64 aborted in 6/6 runs; x86_64 failed 19–38 requests in 6/6 runs.
- Immix with `SCALANATIVE_GC_TRAP_BASED_YIELDPOINTS=0`: arm64 was clean, but x86_64 still corrupted memory in 6/6 trials. A worker then segfaulted, and the GC waited for it to reach a safepoint forever (~2 req/s).
- Boehm: 0 failed requests on both arches (22.0k req/s on x86_64, 14.1k on arm64). The Boehm GC also fixed a crash in Wvlet.

## Decision

- **The example builds with `GC.boehm`.** CI and `bench/build.sh` install `libgc-dev`, and the container image copies `libgc.so.1` from the build machine, since `distroless/cc` has none.
- **The docs recommend Boehm for NativeServer apps**: `docs/http/server.md`, the example README, and the `NativeServer` scaladoc, with links to the upstream issues.
- **uni does not change the GC for users.** The GC is the application's `nativeConfig` choice, and a library can't set it. The env-var yieldpoint switch can't be set from a library either: Scala Native reads it from sbt's environment at link time.
- **Run Boehm with `GC_MARKERS=1 GC_INITIAL_HEAP_SIZE=64m`** (added 2026-11-19, [`plans/2026-11-19-native-server-throughput.md`](../plans/2026-11-19-native-server-throughput.md)). With Boehm's defaults the heap stays ~2.5 MB, so it collects every ~27 requests, and its parallel markers (15 on 18 cores) stop every worker each time; workers then wait on Boehm's global allocation lock ~50x longer than they spend on requests. Together the two settings raised rpc-native throughput 2x to 5x at 16 to 256 connections for ~65 MB more RSS; either alone helped little. The docs, the `NativeServer` scaladoc, the example's container image (`ENV`), and `bench.py` (unless the caller sets them) carry them. uni does not set them itself, for the same reason it doesn't pick the GC, and `GC_MARKERS` takes effect only before `GC_init`. **Revised in #983: uni now sets the marker count itself.** After #981 and #982 cut allocation, one marker alone served 77k–89k req/s against 24k–32k with Boehm's 15, at the same ~11 MB RSS, while `GC_INITIAL_HEAP_SIZE=64m` added only ~15% more for ~65 MB more RSS. So `uni_gc_shim.c` calls `GC_set_markers_count(1)` from a C constructor, before Scala Native's `GC_init`. It finds the function with `dlsym`, so builds without libgc link unchanged (as in ADR 2026-07-06), and `GC_MARKERS` still overrides it, since Boehm reads it at `GC_init` (`GC_NPROCS` doesn't: Boehm uses it only when no count is set). It needs bdwgc 8.2 or later, which added `GC_set_markers_count`; with an older libgc, Boehm keeps its default. The trade-off: an app with hundreds of MB of live data loses parallel marking unless it sets `GC_MARKERS`. `GC_INITIAL_HEAP_SIZE=64m` stays a documented option. **And since #987, a Native HTTP server grows Boehm's heap to 16 MB when it starts** (`GC_expand_hp` through `dlsym`, unless `GC_INITIAL_HEAP_SIZE` is set). With a 2–3 MB heap Boehm collected constantly. On main, a 3.4 KB RPC response went from 47.9k to 71.6k req/s (JVM 93.2k) and an empty one from 94.5k to 102.1k (JVM 104.3k), at 25–27 MB RSS. Only servers do this, so CLI apps keep Boehm's small default.
- **Keep Scala Native javalib slow paths off the request path** (added in #978). Under Boehm, allocation volume limits multi-threaded throughput, and three javalib calls allocate far more on Native than on the JVM: `String.toLowerCase` copies through a `StringBuilder` even for lower-case input (use `HttpMultiMap.lower`), `String(bytes, Charset)` and `getBytes(Charset)` allocate a coder and buffers (use the hibyte `String` constructor or a byte loop for ISO-8859-1), and Scala's `split(Char)` escapes its separator, which misses Native's single-char fast path and compiles a regex per call (use `indexOf`, or Java `split` with a one-char non-meta `String`). These cut Native's allocation from ~44.6 KB to ~25.5 KB per RPC request. To find such sites, break on `scalanative_GC_alloc*` with lldb and group backtraces: `sample` cannot unwind Scala Native frames. Two more rules followed (#981): UTF-8 through a `Charset` allocates a coder per call too (use `wvlet.uni.util.Utf8`, which converts ASCII text directly), and Boehm serves only objects up to about 400 bytes from per-thread free lists, so every larger array takes its global lock (write the response head straight into one exact-size array, not through a `StringBuilder`). With an array-backed `HttpMultiMap` and no boxing or latch on the request path, the RPC request dropped to ~9.2 KB, and CPU per request with the tuned Boehm settings matched the JVM built-in server (~45 µs). Break on `GC_generic_malloc_many` (a free-list refill, so a byte-weighted sample of all small allocations) and `GC_malloc_kind_global` (the lock-taking allocations) to find more.
- **`handleConnection` logs unexpected exceptions at warn.** Disconnects and malformed requests surface as `ReadResult` values, so an exception there is a bug or memory corruption. At debug level it was hidden as dropped connections.

## Consequences

- Throughput drops: about 14k vs 90k req/s on an M5 Pro, and on Linux runners 22.0k (x86_64) and 14.1k (arm64) req/s with Boehm, where Immix reached ~20k and ~32k in the diagnostic runs. The README's build-mode table was measured with Immix.
- The binary links `libgc` in addition to libc, so the "only libc" claim from #833 no longer holds.
- Revisit when a Scala Native release ships the upstream fix (#5159, "Keep the callers' callee-saved registers visible while a thread is stopped", merged 2026-10-29, unreleased): rerun `rpc-bench.yml` with Immix on both arches, and drop this recommendation if it is clean.
