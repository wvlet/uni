# Netty's HTTP/1.1 defenses and features in the socket server

## Context

The socket server in `uni/.jvm-native` (the built-in JVM server and Scala Native, `2026-11-18-jvm-builtin-http-server.md`) had one size limit for headers and body (1 MiB) and a per-read timeout only. It parsed request heads leniently: whitespace before the colon was trimmed, a line without a colon was skipped, `Content-Length: +5` read as 5, and bare CR or LF stayed in values. It also rejected chunked request bodies, ignored `Expect: 100-continue` (curl then waits 1 s before every body over 1 KiB), kept HTTP/1.0 connections open, and did not decode compressed requests or compress responses. uni-netty gets all of these from Netty's pipeline: its HTTP decoder and encoder (`StrictHttpServerCodec`), `RequestReadTimeoutHandler`, `HttpServerKeepAliveHandler`, bounded request decompression, `HttpObjectAggregator`, `HttpContentCompressor`, and `HttpServerExpectContinueHandler`.

## Decision

- **Netty's limits.** The request line is limited to 4 KiB (414), the header block to 8 KiB (431), and the body, as sent or after chunked decoding, to `maxContentLength` (413). The body default stays 1 MiB, as on Native and Node.js, rather than Netty's 64 KiB: lowering it would break apps that accept uploads today.
- **A deadline for the whole request** (30 s, 408), as `RequestReadTimeoutHandler` sets one. The clock starts with the request's first bytes, and the idle timeout still covers the wait before them. Every read waits only for the time left, so a client that trickles a byte every few seconds no longer holds a connection (on Native, one of 16 workers) forever.
- **A write deadline** (30 s). Writes go out in 64 KiB pieces, and a server-wide watchdog aborts a write whose current piece has made no progress for the timeout. On the JVM it closes the socket, which `java.net` does safely under another thread. On Native it calls `shutdown(2)`. A per-piece clock never cuts off a slow but moving client.
- **Strict parsing, as Netty's decoder does, to block request smuggling.** A bare CR or LF, obs-fold, a header name that is not a token (which covers whitespace before the colon), control characters in a value or the request target, a version other than `HTTP/1.x` (505 for other digits), a non-numeric `Content-Length` or more than one value even if they match (Netty 4.2's `allowDuplicateContentLengths` defaults to false), and more than one `Host` (RFC 9112 §3.2) get 400. Method names are case-sensitive, and an unknown one gets 501, as uni-netty answers it. The method is checked after the `Host` and framing headers, so a request with broken ones gets 400 rather than 501, as in uni-netty, whose decoder validates headers first. uni-netty in turn answers a version other than HTTP/1.0 or 1.1 with 505 (400 for a protocol other than `HTTP`) and closes, before the method check; Netty's decoder accepts any `NAME/x.y`. A malformed header still wins there (400), since Netty reports it before handing over the request, while the built-in reader checks the version on the request line first. The request line takes exactly one SP between its words (RFC 9112 §3), and nothing before the method: a run of SP, HTAB, VT, FF, or a bare CR there gets 400 on every server. Netty 4.2's decoder splits on all of these and has no option to stop, so uni-netty's `StrictHttpServerCodec` checks the separators in the decoder's word hooks and fails the request through Netty's own invalid-message path. That is why uni-netty adds Netty's request decoder and response encoder as two handlers, with `HttpServerCodec`'s HEAD/CONNECT method queue and pipelining cap rebuilt around them: `HttpServerCodec` is final and its decoder private. A request without `Host` stays allowed (`2026-10-14-http-server-secure-defaults.md`). Obs-fold is rejected rather than replaced with a space: rejecting is simpler to state in the model and leaves nothing for a front proxy to read differently.
- **Numbers Netty can't parse get 400, not 413.** A `Content-Length` that doesn't fit in a `Long` and a chunk size that doesn't fit in an `Int` are not lengths, so they get 400 as in uni-netty (Netty's `Long.parseLong` and chunk-size parser). A valid number over the limit still gets 413, but a chunk size only once its line is well formed, so `7fffff\n` with a bare LF gets 400 as a malformed line.
- **Chunked request bodies.** Strict hex sizes with an overflow guard, extensions skipped, trailers checked like headers and then dropped. Only the single coding `chunked` is accepted: a final coding other than `chunked` is 400, `chunked` applied twice 400 (RFC 9112 §7.1), any other list ending in `chunked` 501, and `Transfer-Encoding` on HTTP/1.0 400. The handler sees `Content-Length` and no `Transfer-Encoding`, as after Netty's aggregator. A request with both headers is framed by `Transfer-Encoding`, as RFC 9112 §6.3 says, and the connection closes after the response.
- **`Expect: 100-continue`** gets `100 Continue` before the body is read, unless the body has started arriving. A declared body over the limit gets 413 first, and any other expectation 417. HTTP/1.0 ignores `Expect`, as Netty does.
- **Keep-alive as `HttpUtil.isKeepAlive`.** `Connection` is read as a token list. HTTP/1.0 keeps the connection only with `keep-alive`.
- **Request decompression and response compression, on by default as in uni-netty.** gzip and deflate (zlib-wrapped or raw, like Netty's `ZLIB_OR_NONE`) request bodies are decoded before the host check, with the decoded size capped at 64 MiB (413), and a malformed body gets 400. Responses are compressed with gzip or deflate by the q-values in `Accept-Encoding`, as Netty's `HttpContentCompressor` chooses. They are not compressed for HEAD, 1xx, 204, 206, and 304, for bodies that already have a `Content-Encoding`, or for file and SSE bodies. A strong ETag becomes weak, as `IdentityRangeCompressor` does. Unlike Netty, bodies under 1 KiB are not compressed: gzip framing would make them larger.
- **The response writer manages `Transfer-Encoding`** with `Content-Length` and `Connection`, so a handler-set value cannot reach the wire next to the writer's `Content-Length`.
- **WebSocket text and close frames are checked**, as Netty's `Utf8FrameValidator` does. Invalid UTF-8 in a text message or close reason closes with 1007, and a 1-byte close payload or an invalid close code closes with 1002. The check is in the shared `WebSocketFrameDecoder`, so the Node.js server and the Native client get it too.
- **Settings.** Native gets `withMaxInitialLineLength`, `withMaxHeaderSize`, `withRequestReadTimeoutMillis`, `withWriteTimeoutMillis`, `noRequestDecompression`, and `withMaxDecompressedRequestSize` on `NativeServerConfig` and `Native.options`, and `maxRequestSize` now limits the body only. The JVM built-in server keeps fixed defaults (`2026-11-18-jvm-builtin-http-server.md`); apps that need to tune them can add uni-netty. (Superseded by `2026-11-23-shared-server-settings.md`: these limits are now `Http.server` settings on every backend.)
- **The Lean model** (`spec/lean/UniSpec/HttpReader.lean`) follows the reader rule by rule. It proves that a head consumes a prefix of the input, that a `Content-Length` body is exactly the next `n` bytes, that a request always shortens the stream, that both body framings stay within the limit, that repeated `Content-Length` values are rejected, that `Transfer-Encoding` always wins over `Content-Length` and then closes the connection, and that `Transfer-Encoding` on HTTP/1.0 is rejected. It still leaves out the size limits on lines and headers, timeouts, and `100 Continue`.

## Alternatives

- **Netty's 64 KiB body default:** breaks existing uploads; Node.js uses 1 MiB.
- **A cap on concurrent connections:** Netty has none. On Native, each connection still holds a worker, so slow or idle clients can keep all of them busy; the docs point to `withWorkerThreads` and a reverse proxy. The JVM server runs connections on virtual threads.
- **`SO_SNDTIMEO` for the write deadline:** its `timeval` layout differs by OS, and `java.net.Socket` has no write timeout, so one watchdog covers both platforms.

## Consequences

- Native server binaries link zlib (`libz`). examples/rpc-native no longer drops `-lz`.
- A request the old reader accepted can now get 400, 414, 431, 501, or 505, for example `get` in lower case or a request line without a version.
