# S3-compatible object storage in uni

## Context

Users want to read and write objects in S3, the most common object store, and in the services that speak its API (Cloudflare R2, Google Cloud Storage with HMAC keys, MinIO and other self-hosted servers), both directly and for Parquet files. uni-parquet could already read over HTTP Range requests, but S3 needs signed requests, credentials, listing, and multipart uploads. Uni keeps dependencies minimal and runs on the JVM, Scala.js, and Scala Native, so the AWS SDK (JVM only, large dependency tree) was not an option.

## Decision

- **`wvlet.uni.storage` in the `uni` artifact**, depending only on `wvlet.uni.http`. A separate `uni-storage` artifact was considered; the package adds no dependencies, so it stays in `uni`. `ObjectStore` is provider-neutral, so Azure Blob or native GCS OAuth can be added later as other implementations; `S3ObjectStore` is the first.
- **One protocol, many services.** The S3 client is configured by endpoint, region, and path-style addressing. `S3Config.r2`, `S3Config.gcs`, and `S3Config.minio` are presets. The URI scheme (`s3://`, `gs://`) only names the location; the store's config decides which service answers.
- **Pure-Scala SHA-256, HMAC-SHA256, and SigV4.** Scala Native has no `MessageDigest` or `Mac`, so the digests are written in Scala (as `Sha1` is for WebSocket). The signer is checked against the AWS documentation's examples (header signing, query parameters, presigned URLs) and the SigV4 test suite's `get-vanilla`, and on the JVM against `MessageDigest` and `Mac`. Requests carry the real payload SHA-256, not `UNSIGNED-PAYLOAD`, since bodies are in memory (single PUTs and buffered parts) and plain-HTTP servers require it; presigned URLs use `UNSIGNED-PAYLOAD` as AWS specifies.
- **Signing inside the store, not as a generic request filter.** The store builds the wire URI itself (each key segment encoded with RFC 3986 rules) so the canonical request matches exactly what is sent. `HttpClientConfig.requestFilter` sees a request after URI resolution but has no structured key or query, so signing there would mean re-parsing the URI.
- **Redirects are off.** `DefaultHttpClient.handleRedirect` resends the original headers to the `Location` host, so following an S3 redirect would hand a signed `Authorization` to another host. The store uses `noFollowRedirects`, and a 301/307/400 whose `x-amz-bucket-region` differs from the signing region becomes a `WrongRegion` error naming the region; a 400 from the right region keeps S3's own error code. There is no automatic region discovery.
- **Errors.** The HTTP client throws `HttpException` for 3xx and 4xx; the store unwraps the response and maps S3's XML `<Error>` to `StorageException(code, message, statusCode)`. `head` returns `None` for 404 and `delete` treats 404 as success.
- **A private XML reader.** S3 answers listings, multipart uploads, and errors in XML, and Uni has no XML parser. `S3Xml` reads elements and text only (no attributes or namespaces) and is not public; a general XML API would be its own design.
- **Credentials chain in AWS order**: environment, shared `~/.aws` files (`AWS_PROFILE`, `AWS_SHARED_CREDENTIALS_FILE`, `AWS_CONFIG_FILE`), the ECS / EKS Pod Identity container endpoint, then EC2 IMDSv2. The chain remembers which provider answered, so a laptop doesn't probe IMDS on every request; if that provider later fails (a role refresh that times out), the chain scans every provider again rather than surfacing a raw HTTP error. The profile, container, and IMDS providers cache credentials until 5 minutes before they expire (profiles until the process ends), so signing a 1000-part upload doesn't re-read `~/.aws` or call a metadata endpoint per request. `AWS_CONTAINER_CREDENTIALS_FULL_URI` must be HTTPS or a loopback/ECS host, as in the AWS SDKs. Metadata calls use 1–2 s timeouts with no retry. `AwsCredentials.toString` masks the secret and token.
- **More credential sources, in the Java SDK v2 order** (added after the first release). The chain is environment → web identity from the environment (`AWS_WEB_IDENTITY_TOKEN_FILE` + `AWS_ROLE_ARN`, the EKS IRSA path) → profile → container → IMDS. Inside a profile the first match wins: `role_arn` + `web_identity_token_file`, SSO, `role_arn` + `source_profile` / `credential_source`, `credential_process`, then static keys. Java v2 was chosen over botocore because its order is one linear chain; botocore tries a profile `role_arn` before env web identity, and the docs say so.
  - **STS** calls go to the regional endpoint when a region is known. `AssumeRole` is signed with the existing SigV4 signer (service `sts`); `AssumeRoleWithWebIdentity` is unsigned and carries the token in the POST body. The web identity token file is read on every refresh, since EKS rotates it. `source_profile` chains recursively with a loop check, and a profile that sources itself uses its own keys. `mfa_serial` profiles fail: a library can't prompt.
  - **Endpoint overrides** come only from `AWS_ENDPOINT_URL_STS`, `AWS_ENDPOINT_URL_SSO`, and `AWS_ENDPOINT_URL_SSO_OIDC`. The SDKs also honor the generic `AWS_ENDPOINT_URL`, but Uni users often point it at R2 or MinIO, and following it would send web identity and SSO tokens to a non-AWS host.
  - **SSO** reads `~/.aws/sso/cache/<sha1>.json` (SHA-1 of the `sso_session` name, or of `sso_start_url` for legacy profiles) and calls the portal's `GetRoleCredentials` in `sso_region`. An `sso_session` token that has expired or has under 5 minutes left is refreshed through SSO-OIDC `CreateToken`, and the new token is written back, as botocore and Java v2 do. Refresh tokens rotate, so refreshing only in memory could leave the CLI's copy stale, and not refreshing at all would fail long jobs after about an hour. The write goes through a temp file made owner-only (0600) before the token is written, then a rename. Legacy profiles have no refresh token and ask for `aws sso login`.
  - **`credential_process`** runs through `sh -c` / `cmd.exe /C`, as Java v2 and the Go SDK do, so quoting in the user's own config works. It goes through `wvlet.uni.io.IO.run`, which now works on Node.js through `child_process.spawnSync` (loaded at run time, as the Node sync HTTP ADR requires for built-ins). The provider checks the exit code itself rather than using `IO.call`, whose exception carries the command line and stderr.
  - **Errors** name the failed source and the fix, and the chain's `NoCredentials` message lists each failure. Messages never carry a token, secret, command line, or response body: parse errors of credential JSON are dropped, STS errors keep only AWS's code and message, and other exceptions keep one shortened line.
  - **Tests** inject the environment (a private `AwsEnv` lookup), so temp homes and a local `Http.server` playing STS, the SSO portal, and SSO-OIDC replace real AWS. The endpoint tests run on the JVM and Native; on Node.js an in-process server can't answer the synchronous client.
- **Browsers** have no environment, files, or instance metadata, so they use explicitly passed (ideally temporary) keys or presigned URLs. The docs warn against shipping long-lived keys.
- **Node.js response cap.** The Node sync channel sizes a fixed buffer from `maxResponseBytes` (`2026-05-14-nodejs-sync-http.md`), so ranged reads are split into requests below it on every platform (64 KiB under the cap, or half of a cap under 128 KiB), and a whole-object `get` on Node reads by ranges after a HEAD.
- **Multipart uploads** buffer one part (8 MiB by default, at least 5 MiB), upload parts sequentially, and complete on `close()`. A stream that never fills a part sends one PUT. `ObjectOutputStream.abort()` discards the upload; an exception while writing aborts it too. uni-parquet's writer calls `abort()` instead of `close()` on its output when it fails, and `ParquetWriter.abort()` lets callers do the same, so a failed write never publishes a partial file. Parallel part uploads are left for later.
- **Native curl sends empty PUT and POST bodies** with `POSTFIELDS ""` and size 0. Before, curl read a POST body from stdin and sent a bodyless PUT with no `Content-Length`, which S3 rejects with 411 (zero-byte objects and `CreateMultipartUpload`).
- **CI integration tests use the Versity S3 Gateway**, downloaded as a pinned, checksum-verified release in the JVM job. It verifies SigV4 signatures and stores buckets as directories. MinIO was the first choice, but it no longer publishes community binaries or official images, and third-party mirrors are a supply-chain risk. The tests are skipped unless `UNI_S3_TEST_ENDPOINT` is set, so they also run locally against any S3-compatible server, and they pass on the JVM, Scala Native, and Node.js.

## Consequences

- `Parquet.openS3` / `openS3Async` and `ByteSource.ofS3` / `ofObject` read Parquet from any S3-compatible store; `Parquet.newWriter[A](store.newOutputStream(uri))` writes to one.
- Only the JVM CI job runs the integration tests; Native and Node.js were verified locally.
- Adding Azure Blob means another `ObjectStore` with its own signer (SharedKey or SAS); SAS URLs already work with `ByteSource.ofUrl`.
